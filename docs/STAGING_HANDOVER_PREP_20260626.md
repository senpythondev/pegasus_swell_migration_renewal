## 1. 外部アクセスの可否

### 判定：✅ 外部から到達可能（ポート開放は不要）

- **ホストの公開IP = `220.158.21.114`**（このサーバー自身のグローバルIP。NAT背後ではなく直接付与）。
- ポート待受状態（`0.0.0.0` = 全インターフェース公開）:

| ポート | サービス | 用途 | 外部公開 |
|---:|---|---|:---:|
| 8080 | nginx（WordPress） | サイト本体・管理画面 | ✅ 公開 |
| 8081 | phpMyAdmin | DB管理 | ✅ 公開（⚠️） |
| 8025 | mailpit Web UI | テストメール閲覧 | ✅ 公開 |
| 1025 | mailpit SMTP | メール受信口 | ✅ 公開（⚠️） |

- **外部到達の実証:** 外部のリーダープロキシ（VPS外のサーバー）から `http://220.158.21.114:8080/` を取得 → **HTTP 200、ページタイトル「一般社団法人ペガサス | 全国対応」を確認**。＝ インターネット側から問題なく閲覧できる。
  - 補足：HTTPS強制のツールで叩くと `ECONNREFUSED` になるが、これは **8080がHTTP専用（TLS無し）** のため。プレーンHTTPなら到達する。
- 結論：**ペガサス様は `http://220.158.21.114:8080/` をブラウザに入れればそのまま閲覧可能。ポート開放等の追加作業は不要。**

### 注意点（HTTPであること）
- 本ステージングは **HTTP（暗号化なし）**。検収用途では許容範囲だが、ログイン情報が平文で流れるため、**管理画面ログインは信頼できる回線で**行う旨を案内。
- 本番は SSL（HTTPS）必須（カットオーバー時に対応）。

### ファイアウォールについて（要確認事項）
- ホストの `ufw`/`iptables` の精査には管理者権限が必要で、本セッションでは確認できなかった（sudo不可）。
- ただし**外部からの実アクセスが200で成立している**ため、結果として 8080 は外部開放されている（＝検収には支障なし）。
- → むしろ問題は「**開きすぎ**」（§3）。管理系ポートを閉じる方向の対応が必要。

## 2. 検索エンジン対策（インデックス拒否）

### 判定：✅ 有効（重複コンテンツ回避OK）

| 項目 | 状態 |
|---|---|
| WordPress設定「検索エンジンがインデックスしないようにする」 | ✅ **ON**（`blog_public=0`） |
| 各ページの robots メタ | ✅ 全ページ種別で `noindex, nofollow`（トップ/固定ページ/CPTアーカイブ/CPT個別/フォームページで確認） |

- **`noindex, nofollow` が全ページに出力**されているため、Googleはステージングをインデックスしない（本番との重複コンテンツは回避できる）。これが最も信頼できる防御。

### 補足（robots.txt）
- `/robots.txt` は現在 `Disallow: /wp-admin/` 等の**通常（公開向け）内容**で、`Disallow: /`（全拒否）は出ていない。
  - 理由：**WP-Optimize が robots.txt をフィルタ**しており、`blog_public=0` 本来の `Disallow: /` を上書きしているため。
- ただし**インデックス可否を決めるのはページ単位の `noindex` メタ**であり、こちらは全ページで有効。よって**インデックスされる懸念は実務上なし**。
- （任意）より厳格にするなら、Basic認証（§3）でクローラー自体を遮断するのが確実。Basic認証を掛ければ robots.txt の論点は不要になる。

> 本番移行時は逆に `blog_public=1`（インデックス許可）へ戻すこと。カットオーバーチェックリストに留意点として追加済み相当。

## 3. アクセス制限の検討（最重要・セキュリティ）

### 現状：⚠️ 無防備（URLを知れば誰でもアクセス可能）

- nginx に **Basic認証なし／IP制限なし**（`nginx.conf` に `auth_basic` 無し）。
- 加えて、**管理系サービスが外部公開**されている：

| 公開物 | リスク |
|---|---|
| phpMyAdmin（:8081） | **最重要。** DB管理画面がインターネットに露出。ログイン総当たり・脆弱性攻撃の標的になりうる |
| mailpit Web UI（:8025） | テスト送信メール（フォーム入力内容＝個人情報）が誰でも閲覧可能 |
| mailpit SMTP（:1025） | 外部に空きSMTP口。踏み台化の懸念（mailpitは中継しないが、ポート露出自体が不要） |
| WordPress 管理画面（:8080/wp-admin/） | ログイン画面が露出（総当たり対象） |

### 推奨（適用は要承認）

**推奨A（最優先）：サイト全体に Basic認証 ＋ 管理系ポートを内部限定に。**

1. **nginx に Basic認証**を掛け、ペガサス様にだけ ID/パスワードを渡す（検収者限定）。
   - 用意するもの：`.htpasswd`（例 `htpasswd -c /etc/nginx/.htpasswd pegasus`）。
   - `nginx.conf` の `server` ブロックに:
     ```nginx
     auth_basic "Staging - Pegasus Kensho";
     auth_basic_user_file /etc/nginx/.htpasswd;
     ```
   - 反映は **`docker compose restart nginx`**（単一ファイルbind-mountのため reload では反映されないことがある）。
   - ※ CF7のREST送信やajaxに支障が出る場合は `location` 単位で `admin-ajax.php` 等を除外。検収では通常問題にならない。
2. **phpMyAdmin（8081）・mailpit（8025/1025）を外部から閉じる**：
   - `docker-compose.yml` のポート公開を `127.0.0.1:8081:80` / `127.0.0.1:8025:8025` 等の**ループバック限定**に変更（→ SSHトンネル経由でのみ閲覧）。
   - または最低限、ホストファイアウォールで 8081/1025 を遮断。
   - mailpit（8025）は検収でフォーム結果を見せるために使うなら、**Basic認証付きで8025だけ残す**か、検収時のみ大野様が画面共有で見せる運用も可。

**推奨B（簡易）：IP制限。**
- ペガサス様の固定グローバルIPが分かるなら、nginx で当該IPのみ `allow`、他は `deny`。
- 長所：橋本様はID/PW不要。短所：先方IPが変動するとアクセス不可。

> いずれも**設定変更を伴う**ため、本書では現状報告と方法提示にとどめ、**適用可否のご判断を待つ**。ご承認いただければ Basic認証（推奨A-1）を最小リスクで適用する。

## 4. テスト設定が検収の妨げにならないか

### 結論：検収自体に支障なし。ただし「フォームのメールは実際には届かない」点の事前説明が必須。

| テスト設定 | 検収時の挙動 | 説明の要否 |
|---|---|---|
| **mailpit ＋ Code Snippets id=6（テストSMTP）** | フォーム送信は成功（「送信されました」表示）するが、**メールは実際の受信箱に届かず mailpit（:8025）に溜まる** | ✅ **要説明**。「ステージングでは実送信せず、テスト用に全メールを mailpit で受け止めています。届いたメール内容は :8025 で確認できます」 |
| Flamingo（送信データ保存） | 送信内容は管理画面 Flamingo に保存され、後から確認可 | 任意で案内 |
| 確認画面/完了URLの301転送 | 旧確認/完了URLは入力ページへ転送される（移行仕様どおり） | 必要なら案内 |

- → **橋本様がフォーム動作を試す場合、「実際のメールは届きません。届いたかは mailpit で確認します」と必ず伝える。** これを伝えないと「メールが来ない＝不具合」と誤解される恐れ。
- 本番では id=6 を無効化し実SMTPで配信（カットオーバーチェックリスト §最重要#3）。

## 7. セキュリティ上の懸念（明確化）

1. **phpMyAdmin（:8081）の外部公開＝最大の懸念。** DB管理画面がインターネットに露出。早急にループバック限定 or ファイアウォール遮断を推奨。
2. **mailpit（:8025）にフォーム入力（個人情報）が誰でも閲覧可能。** Basic認証 or 非公開化を推奨。
3. **サイト全体が無認証で公開。** 検収者限定にするため Basic認証/IP制限を推奨。
4. HTTP（平文）であること。検収では許容だが、本番はHTTPS必須。
5. インデックス拒否は有効だが、robots.txt は全拒否になっていない（noindexメタで担保。§2）。

> 上記1〜3の対策（特に phpMyAdmin の遮断と Basic認証）は、**ご承認いただければ速やかに適用可能**です。設定変更を伴うため、本書では提案にとどめています。
