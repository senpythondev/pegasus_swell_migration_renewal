## 0. 結論サマリー（先に重要な2つの現実制約）

1. **⚠️ 無料版 Code Snippets ではネイティブCSSスニペットが作れない。** 現在 v3.9.6（無料）で、`class-snippet.php` の `get_is_pro()` が **css / js / cond を Pro専用**と判定。→ 「Code SnippetsのCSS」を文字通り実現するには **(A)WPカスタマイザー『追加CSS』／(B)Code Snippets Pro導入／(C)無料版＋PHPスニペットでCSS出力** のいずれかを選ぶ必要がある（§4）。
2. **⚠️ 1つのCSSルール内に『構造』と『装飾』が混在**しており、**プロパティ単位で厳密に2層へ割るのは非現実的**（断片化・カスケード/詳細度事故・表示崩れリスク大）。→ 振り分けは**「セクション/責務」の粗い粒度**で行うのが現実的（§4）。

→ **推奨:** 装飾層(③)は **カスタマイザー『追加CSS』を第一候補**（無料・標準・ペガサス様が管理画面で編集可・上書き最強）。厳密全分割はせず、**「運用で実際に触る装飾（色・主要余白・フォント・ホバー）」を優先的に外出し**し、細かな構造依存装飾は土台(②)に残す**折衷**が、保守性・安全性・現実性のバランス最良。ヘッダーは**命名スコープ強化＋最小テンプレ上書きの文書化**で対応（フックは該当位置に存在しないため単純置換不可）。

## 4. 重要な制約と、装飾層(③)の実現方式の選択

### 制約A：プロパティ単位の厳密分割は不可
1ルール内に構造＋装飾が混在（§1・§実測）。厳密に割ると①同一要素のCSSが2層に分断→可読性低下②詳細度/読込順の事故で崩れやすい③保守が難しくなる（橋本様の目的＝保守性向上に逆行）。→ **「セクション/責務」の粗い粒度**で分ける。

### 制約B：無料Code SnippetsはネイティブCSS不可 → ③の実現は3択
| 案 | 内容 | 長所 | 短所 | 推奨度 |
|---|---|---|---|:---:|
| **(A) カスタマイザー『追加CSS』** | WP標準の追加CSSに装飾CSSを置く | 無料・標準・**管理画面でペガサス様が編集可**・`wp_head`最後に出力＝上書き最強・プレビュー可 | 1テキスト枠で巨大化すると見づらい（→ セクション見出しコメントで整理） | ★★★ |
| **(B) Code Snippets Pro** | 有料版でネイティブCSSスニペット | RFPの「Code Snippetsに集約」に文字通り沿う・スニペット単位で整理/ON-OFF | **有償**・大量CSSはinline出力で毎ページhead肥大（キャッシュ不可） | ★★ |
| **(C) 無料版＋PHPスニペット** | PHPスニペットで`wp_head`に`<style>`出力 | 無料でCode Snippetsに置ける | CSS-in-PHPで可読性低・シンタックス支援なし・巨大化で編集困難 | ★ |

> **見解:** 橋本様の「Code Snippetsに集約」の**本意は『装飾を管理画面で安全に運用調整できること』**。それを最も無理なく満たすのは実は **(A)カスタマイザー追加CSS**（無料・標準・ペガサス様が触れる）。RFP文言に厳密に合わせるなら (B) Pro。**どちらを採るか大野様・橋本様の判断が必要**（§9）。

### 性能・管理上の是非（橋本様の懸念に回答）
- **91KB全部を③(inline)に移すのは非推奨**（毎ページhead inline・ブラウザキャッシュ不可・巨大テキスト編集困難）。
- → **③に載せるのは「運用で実際に触る装飾」に限定**：ブランド色・主要な余白/フォント・ボタンやカードの色/ホバー等、**変更頻度が高い部分**。細かな構造連動の装飾は②に残す。これで③は数百行規模に収まり、性能・編集性を確保。

## 6. ヘッダー：命名規則改善・フック方式化の方針

### 命名（SWELL内部クラス競合回避）
- **現実:** ヘッダー/ナビ/SPメニューは**SWELLが生成する要素**で、そのクラス（.l-header/.c-gnav/.p-spMenu等）を完全に使わずデザイン変更するのは困難。→ 「.pega-*へ全面改名」は不可（SWELLの出力クラスは改名できない）。
- **現実解（推奨）:**
  1. **スコープ用ラッパー**：ヘッダーに `.pega-header`（または body の `.pega-top`）を付け、全ヘッダー上書きを `.pega-top #header .l-header__logo{…}` の形に統一（現状 `.home #header` 相当を明示的ブランド名に）。→ 影響範囲を宣言的に限定。
  2. **新規要素は `.pega-*`**：連絡先ブロックは `.pega-header-contact`（**既に対応済**）。今後追加する独自要素も `.pega-*`。
  3. **上書き対象のSWELLクラス一覧を文書化**（本書§2）し、**SWELL更新時に再点検**（移行チェックリストへ）。
  4. 可能な範囲は**SWELLカスタマイザーのヘッダー設定**（配色・レイアウト・CTAボタン）へ寄せ、CSS上書きを削減。

### テンプレ上書き→フック方式（連絡先注入）
- **調査結果:** 連絡先を差し込む位置（`.l-header__logo` 内）に **SWELLの `do_action` フックは存在しない**（ヘッダー領域のフックは `swell_before_post_head` 等の記事用のみ）。→ **単純なフック置換は不可**。
- **選択肢:**
  - (a) **最小テンプレ上書きを維持**（現状の1行注入）＋**git追跡**＋「**SWELL更新時に header_contents.php のコア差分を確認**」を移行チェックリストへ明記。**最も現実的・低リスク**。
  - (b) JSで `.l-header__logo` に連絡先を後付け注入（テンプレ非依存だが別の脆さ・FOUC懸念）。
  - (c) SWELLヘッダーの**CTAボタン枠**へ「お問い合わせ」単一ボタンとして寄せ、受付時間/TELは別扱い（連絡先ブロック全体は枠に不適）。
- **推奨:** **(a)**。テンプレ差分は極小（コメント除けば実質1行）で、更新時確認をルール化すれば実害は小さい。

## 7. 作業規模・リスク・段階手順

### 規模感
| 作業 | 規模 | リスク |
|---|---|---|
| ③の方式決定（A/B/C）＋読込順確認 | 小 | 低（要・意思決定） |
| 装飾のセクション単位外出し（②→③） | **中〜大**（10+セクション・数百行） | 中（読込順/詳細度で崩れ得る→要視覚回帰） |
| ヘッダーCSSのスコープ統一（命名） | 中（約120箇所） | 中〜高（ヘッダーは繊細） |
| テンプレ上書きの文書化＋git追跡 | 小 | 低 |
| フォント等の標準管理寄せ | 小 | 低 |

### 段階手順（推奨）
1. **③方式を決定**（推奨：カスタマイザー追加CSS）／読込順を検証。
2. **セクション1つで試行**（例：commuteバナー等・独立性高い所）→ 装飾を③へ移し、視覚回帰（スクショ比較）で無崩れ確認。手順を確立。
3. **本体セクションを順次**②→③へ（1セクション＝1コミット＝1回帰確認）。
4. **ヘッダー**は最後に、スコープ統一（命名）＋文書化。テンプレ上書きはgit追跡＋チェックリスト追記。
5. 各段階で全ページ200・レイアウト無崩れを確認。**移行中に崩さないため必ず1セクションずつ**。

### リスク低減
- 各ステップ前にstyle.cssをバックアップ、各ステップ後にスクショ差分。
- 読込順（③が②を上書きできる順）を最初に固定。
- ヘッダーは影響大のため単独ステップ・入念確認。

## 8. 注意点・懸念（バランス）

- **3層で逆に複雑化しないか:** 厳密全分割は複雑化・崩れリスク大 → **粗い粒度＋『運用で触る装飾のみ③』**に留めるのが最適バランス。②は行数が多くても「安定した土台」として許容（頻繁に触らない）。
- **③にCSS大量投入の是非:** inline肥大・キャッシュ不可・編集困難のため**全量投入は避ける**。運用調整対象（色・主要余白・フォント・ホバー）に限定。
- **標準管理に寄せられる部分:** メニュー/主要色/ロゴ/SPメニュー挙動は**既に標準管理へ移済**。フォントは寄せ余地あり。装飾の一部（追加CSS）は「標準機能(カスタマイザー)」で運用可＝実質①寄り。
- **RFP文言との整合:** 「Code Snippetsに集約」を厳密に満たすなら Pro が要る。**本意（安全な運用調整）**はカスタマイザー追加CSSでも満たせる。→ この解釈を橋本様に確認いただくのが最短。
