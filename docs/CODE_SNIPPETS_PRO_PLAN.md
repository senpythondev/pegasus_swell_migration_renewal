**作成日:** 2026年7月9日
**前提:** 橋本様のご指摘に沿い、装飾CSSをCode Snippetsで管理するため Code Snippets Pro（年額約$39）購入を決定。**本タスクは購入前の確認・計画のみ（購入・実装は後）。**

## A. 購入前チェック：確実にCSSスニペットが使えるか

### A-1. CSSスニペットは確実に使える（コードで確認済）✅
- `class-snippet.php` の `get_types()` に **`css`** を含む（`php, html, css, js, cond`）。CSSスニペットのscopeは **`site-css`（フロント）/ `admin-css`（管理）** が定義済み。
- 無料版では `get_is_pro()` が **css/js を Pro専用**と判定してロック（現状使えない）。→ **Pro化でこのロックが外れ、CSSスニペットが登録・実行可能**になる。
- **結論:** Pro購入で、装飾CSSを**セクション単位のCSSスニペットとして登録・管理できる**（購入は無駄にならない）。

### A-2. Pro導入方法（無料版からの移行・データ保持）✅
- **プラグイン内蔵の「バージョン切替（Version Switch）」機能あり**（`class-version-switch.php`：`get_available_versions()` が版一覧＋DLリンクを取得し、AJAX `code_snippets_switch_version` で**その場で版を切替**）。→ **ライセンス購入後、管理画面からPro版へその場でアップグレード可能**（手動再インストール不要）。※または Pro版zip を手動アップロードでも可。
- **同一プラグイン・同一DBテーブル（`wp04447asnippets`）を使用。** テーブルには既に **`revision`・`cloud_id` 列が存在**＝Pro前提のスキーマ。→ **既存スニペットは完全に保持**（下記A-3）。ライセンスキーを設定→Pro機能有効化。
- **既存無料版で管理中のもの（Pro移行で影響を受けないか）:** 現在アクティブなPHPスニペット4件（**id5 CF7確認欄／id6 テストSMTP／id7 メールリンク／id8 コアサイトマップ**）＋停止中4件。**PHPスニペットは無料/Pro共通で動作**し、同一テーブルのため**Pro化後もそのまま動く**（影響なし）。

### A-3. パフォーマンス：inline肥大を避けられるか（重要）
- **証拠（readme + DBスキーマ）:** readmeに「**CSS/JSスニペットの“リビジョン番号”を『Reset Caches』で更新（PRO）**」。DBテーブルに **`revision` 列**。→ **ProはCSS/JSを“リビジョン付きでキャッシュ管理”**して出力する（毎回パースの生inlineではなく、**バージョン付きでブラウザキャッシュが効く**出力）。「inline肥大」の主懸念（キャッシュされず毎ページ重複）に対し、**キャッシュ機構で緩和される**。
- **正直な留保:** Proの出力コード自体は無料版に含まれない（Pro専用）ため、「外部ファイル(`<link>`)出力か／キャッシュ付きinlineか」の**厳密な出力形態は、Pro導入後に設定画面で最終確認**したい（購入前にコードから断定はできない）。ただし上記の**リビジョン/キャッシュ機構は確認済**で、キャッシュ最適化の仕組みは備わっている。
- **いずれにせよの緩和策:** ①**Code Snippetsに載せる装飾は“運用で触る量”に限定**（全91KBは載せない）②WP-Optimize（導入済）でCSS最適化③トークン中心設計（下記B）で装飾スニペットを小さく保つ。→ **実運用で問題化しない設計にできる。**

> **A まとめ:** CSSスニペットはPro化で確実に使える。移行は内蔵Version Switchで在place・既存PHPスニペット保持。パフォーマンスはリビジョン/キャッシュ機構＋量の抑制で対処可能（出力形態の最終確認は導入後に）。**購入は妥当。**

## B. CSS 3層振り分け 具体計画（トークン中心・現実的）

**方針:** プロパティ単位の厳密分割は非現実的（1ルールに構造＋装飾が混在）。→ **「設計トークン＋装飾ルール」をCode Snippetsに、構造・骨格を子テーマに** という**トークン中心設計**を採用。現状すでに `var(--pega-*)` を多用しており移行が容易。

### 3層の内訳
| 層 | 置き場所 | 中身 | 概算ボリューム |
|---|---|---|---|
| ① 標準管理 | 外観>メニュー / SWELLカスタマイザー | メニュー・メインカラー・ロゴ・SPメニュー挙動（**移済**）／フォントは寄せ余地 | CSS外 |
| ② 子テーマ style.css（土台） | `swell_child/style.css` | 構造・レイアウト骨格・grid/flex・レスポンシブ`@media`骨格・`position/z-index`・full-wide/constrained骨格・SWELL既定リセット。**装飾値は `var(--pega-*)` を参照** | 約 **2,300〜2,800行**（骨格中心） |
| ③ Code Snippets（site-css・装飾） | Pro CSSスニペット | **(a) 設計トークン**（`:root` の色/余白/フォント/角丸/影 変数）＝運用調整の主入口／**(b) セクション別の純装飾ルール**（背景・グラデ・ホバー・色の載せ替え等） | 約 **1,200〜1,700行** |

> 行数は概算（1ルール混在のため、実際は「トークン＋純装飾ルール」を抽出しながら確定）。**目安：装飾トークン＋純装飾で全体の3〜4割をCode Snippetsへ、骨格6〜7割を子テーマに。**

### Code Snippets（③）の整理単位（スニペット構成案）
1. **`pega-tokens`（site-css・最優先）** … `:root{ --pega-* }`（色3色＋派生、余白スケール、フォント、角丸、影）。**運用で色・余白・フォントを変えるならここ1枚**。← 橋本様の「運用で触る」核心。
2. **`pega-sec-hero`** … ヒーローの装飾（背景グラデ・コピー影・ボタン装飾・ホバー）
3. **`pega-sec-concerns`** / **`pega-sec-bridge`** / **`pega-sec-homeworker`** / **`pega-sec-reasons`** / **`pega-sec-commute`** / **`pega-sec-voices`** / **`pega-sec-column`** / **`pega-sec-cta`** / **`pega-sec-footer`** / **`pega-sec-floatcta`** … 各セクションの純装飾。
4. **`pega-header-deco`** … ヘッダーの装飾（ロゴ色/影・ドロップダウン配色・ハンバーガーパネル配色・連絡先見た目・ホバー）。※構造は②。
- スニペットは**ON/OFF・優先度管理可**。1セクション=1スニペットで、将来ページ追加も同形式で拡張。

### 読込順（③が②を上書きできること）
- 子テーマ style.css は `wp_enqueue_scripts`（優先度11）でenqueue。Code Snippets の site-css は Pro が管理する出力（wp_head系）で、**通常 enqueue済スタイルの後に出る**ため③が②を上書き可能。→ **導入直後に読込順を1回検証**して確定（崩れ防止の前提）。

## C. ヘッダーの整理方針

### C-1. 命名スコープ化（SWELL内部クラス競合回避）
- 現状：ヘッダーで **SWELL内部クラス約120箇所を上書き**（`.l-header__*`19／`.c-gnav`等47／`.p-spMenu`26／`.swell-block-*`45）。既に `.home #header …` でスコープ済。
- **方針：** ブランド名スコープに統一 → `.pega-top #header .l-header__logo{…}`（body に `.pega-top` 付与 or 現行 `.home` を明示ブランド化）。**新規要素は `.pega-*`**（連絡先＝`.pega-header-contact` 済）。**SWELL出力クラス自体は改名不可**なので、上書き対象クラス一覧（本書C参照）を**文書化しSWELL更新時に再点検**。
- 可能な範囲はSWELLカスタマイザーのヘッダー設定へ寄せてCSS上書きを削減。
- 構造（flex/order/ブレークポイント）は②、装飾は③（`pega-header-deco`）へ。

### C-2. テンプレ上書き（`header_contents.php`）
- 前回結論どおり：**注入位置（`.l-header__logo`内）にSWELLフックが存在しない**ため完全撤去は不可。→ **最小上書き（実質1行）を維持＋git追跡＋「SWELL更新時にコア差分確認」を移行チェックリスト化**。低リスク。

## D. 作業の段取り・リスク

### 段取り（崩さないための順序）
1. **Pro導入（Version Switch）→ ライセンス有効化 → 読込順を検証**（③が②を上書きできるか）。
2. **`pega-tokens` を先に作成**（③）。子テーマの `:root` を移動し、参照は既に `var(--pega-*)` のため**見た目不変を確認**（トークン移動だけなら低リスク）。
3. **独立性の高い1セクションで試行**（例：`pega-sec-commute`）→ 純装飾を③へ移し、**スクショ差分で無崩れ確認**。手順確立。
4. **本体セクションを順次**（1セクション＝1スニペット＝1コミット＝1視覚回帰）。
5. **ヘッダー**は最後（命名スコープ統一＋`pega-header-deco`）。テンプレ上書きは文書化＋git追跡。
6. 各段階で全ページ200・レイアウト無崩れ確認。

### リスクと低減
| リスク | 低減策 |
|---|---|
| 読込順で③が効かない/効きすぎる | 導入直後に順序検証・必要なら優先度調整 |
| 移行中の表示崩れ | 1セクションずつ・都度スクショ差分・style.cssバックアップ |
| ヘッダーの繊細さ | 単独ステップ・入念確認・SWELL内部クラス一覧を管理 |
| Pro出力形態（inline/file）想定違い | 導入後に設定確認・量を抑制・WP-Optimize併用 |

## E. PHP機能のCode Snippets集約（提案書の約束との整合）

現行の独自PHPの所在：
| 種別 | 現在の場所 | Code Snippets集約の要否・見解 |
|---|---|---|
| CF7確認欄検証／テストSMTP／メールリンク／コアサイトマップ | **Code Snippets（id5-8・有効）** | ✅ **既に集約済**（提案書どおり） |
| 資料請求トークンシステム | **mu-plugin**（`pega-download-system.php`・DBテーブル＋rewrite＋readfile） | 自己完結の“ミニプラグイン”。Code Snippetsへ移設も可能だが、**mu-pluginの方が適切**（DB作成・独立性）。要相談 |
| フッター/追従CTA/ヘッダー連絡先の**描画関数** | **子テーマ functions.php**（`pega_render_footer_*` / `pega_render_sticky_cta` / `pega_render_header_contact`） | テーマ描画PHP。**functions.phpが自然な置き場**。厳密に「全PHPをCode Snippets」とするなら移設可だがテンプレ結合が強く、要方針確認 |
| リダイレクト | **Redirectionプラグイン**（PHPコードではない） | プラグイン管理で適切 |

> **見解:** 「機能系PHP」は既にCode Snippetsに集約済。**「テンプレ描画系PHP」は functions.php が妥当**で、無理にCode Snippetsへ移すとテンプレ結合が見えにくくなる恐れ。**どこまでをCode Snippets集約対象とするか（機能系のみ／描画系も含むか）を橋本様に確認**するのが良い。
